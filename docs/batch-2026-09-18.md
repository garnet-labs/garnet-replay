# Batch 2026-09-18: six ordinary changes, three dependency changes, and the harness gaps they surfaced

Harness at `dedf8f6` (merge of pull request 12). All writes went to `garnet-labs/*`
forks; upstream stayed read-only. Every fork pull request is a draft with two
commits: commit 1 carries the touched paths at the change's base plus the
recording workflow, commit 2 carries the change.

This document is a ledger, not a finding. Every comparison below is rated
`undeterminable (incomplete)` by `replay card` because no record declares
capture completeness. Destination deltas are observed differences between two
runs, not attributed effects of the change.

What the three records show:

- The install chains are identical across commits in all three pairs: `node` →
  `registry.npmjs.org`, `uv` → `dualstack.python.map.fastly.net`. A version
  change inside the same registry does not change a process or a destination,
  so the record has nothing to show for it. esbuild's install script produces
  no line of its own in either commit.
- The only substantive-looking delta, `chrome` and `storage.googleapis.com`
  disappearing on continue 5, is the `core/node_modules` cache: commit 1 missed
  and installed core (Puppeteer downloaded Chrome), commit 2 hit the cache that
  commit 1 populated and skipped `npm ci` entirely. The change touched
  `extensions/cli`, not `core`. Gap 9 in the strongest form: the first run of a
  pair populates the cache the second run hits.
- Every remaining line is Actions storage (`blob.*.store.core.windows.net`,
  `productionresultssa*.blob.core.windows.net`) or runner background
  (`provjobd`, `hosted-compute-*`, cloud metadata). Gap 11.
- Both continue jobs ran four Linux legs (Node 18 / 20 / 22 / 24) and the
  servers job ran three package legs; each comment reads `1 job`. Gap 10, third
  reproduction.

Reading against the hypothesis ("a dependency change whose install-time
behaviour differs shows an attributable process or destination the diff does
not show; a change with no such difference shows nothing beyond noise"): the
second half held (treatment and control alike showed nothing attributable), the
first half was not exercised, because none of the three changes altered which
processes run or where bytes come from. `find` ranks every manifest-plus-lockfile
change as `install-time execution surface changed` (+3), which does not
separate the class the record can see from the class it cannot (gap 12). Among
the 105 open Dependabot changes on continuedev/continue and the six on
modelcontextprotocol/servers, none inspected adds or removes a package with an
install script or moves a download to a new host. The next test of the first
half needs either a real change of that class, found with a registry
`hasInstallScript` check, or an authored transition (`live <slug> --dependency
<name> --to <version> --package-dir <dir>`) labelled as authored.

## 3. Harness gaps, with reproduction and code sites

Nothing below was fixed in this batch. Each item names the symptom, how to
reproduce it, where the behaviour lives, and the smallest change that would
close it. The sandbox transport shim mentioned under gap 2 lives outside the
harness and is not part of this change.

### Gap 1: `refresh` has no conflict path

- Symptom: `replay refresh <slug>` fails closed with `refresh-merge failed:
  merge conflict in ...` whenever fork-only `.github/` edits on main collide
  with upstream. Three of three refreshed forks hit it (open-swe `ci.yml`,
  `pyproject.toml`; cline `publish.yml`, `test.yml` deleted upstream,
  `hooks.ts`; codex `sdk.yml`).
- Code: `lib/replay-pr.mjs:494` (`refresh-merge` step) and
  `lib/replay-pr.mjs:1333-1340` (error path).
- Proposed: a `--theirs-for <glob>` (or `--prefer-upstream`) option that resolves
  conflicts in favour of upstream for matching paths only, records each resolved
  path in the ledger, and still fails closed on anything unmatched. Test: a
  fixture repository with a conflicting `.github/workflows/x.yml`.

### Gap 2: `verify` / `card` / `receipt` hard-code `https://api.github.com`

- Symptom: behind a GitHub API proxy (`GH_HOST` set, token valid only there)
  the three commands 401 while `gh` and `git` work.
- Code: `lib/verify.mjs:171`, `lib/receipt.mjs:89`, `bin/replay.mjs:223`.
- Proposed: one `apiBase()` helper honouring `GITHUB_API_URL`, then `GH_HOST`
  (`https://${GH_HOST}/api/v3`), then the default. Test: set `GITHUB_API_URL`
  and assert the request URL.

### Gap 3: vocabulary guard matches substrings

- Symptom: `banned vocabulary 'clean' in renderer-owned copy` on the upstream
  title `... disable cleanup ...` (opencode 49811).
- Code: `lib/guards.mjs:96-103` (`assertVocabClean`, `lower.includes`).
- Proposed: word-boundary match (`\b${term}\b`, case-insensitive) and a test
  with `cleanup`, `cleaner`, `unclean` passing while `clean` alone still fails.

### Gap 4: candidate selection does not check the base branch

- Symptom: `find` lists changes whose base is a stacked branch or a release
  branch; `live` then stops with `main on the fork is N commit(s) behind the
  change's base` (cline 14160, opencode 49792).
- Code: `lib/replay-pr.mjs:417` and `:1364` (the distance guard fires late, in
  `live`); `find` never reads `base.ref`.
- Proposed: `find` prints `base: <ref>` per row and skips non-default bases
  unless `--any-base` is passed. Test: fixture pull requests with mixed bases.

### Gap 5: `find <slug>` on a fresh target demands the upstream and `--fork`

- Symptom: after `replay fork <slug>` created `targets/<slug>.json`, `find
  <slug>` still says `new target '<slug>' needs --fork <owner/repo>`.
- Code: `lib/ledger.mjs:59`.
- Proposed: read `upstream` and `fork` from the ledger when present. Test:
  ledger fixture, `find` without extra arguments.

### Gap 6: fork-only `.github/scripts/*.mjs` fail upstream lint on every replay pull request

- Symptom: open-swe `JS lint` / `JS format check` fail on
  `.github/scripts/garnet-dependabot-*.mjs` (fork-only, August), on every replay
  pull request; verify reports the check as unsettled or failed.
- Proposed: keep fork-only scripts out of upstream lint paths (a
  `.eslintignore` / `.prettierignore` entry added by `refresh`, or move scripts
  under `.garnet/`), and make verify distinguish checks that fail on fork-only
  paths from checks that fail on the change.

### Gap 7: a single-path change on a fork with a recorder cannot be replayed

- Symptom: `garnet-labs/codex@main already holds the touched paths as the
  change found them and commit 1 has nothing else to stage; pass --first
  <path>` for codex 35882; the only touched path is the change itself, so
  `--first` would leave commit 2 empty.
- Code: `lib/replay-pr.mjs:372`.
- Proposed: when the fork lacks `.github/dependabot.yml`, let default mode add
  it in commit 1 (inject mode already does); otherwise allow an explicit
  `--carrier <path>` that stages a documented no-op file under `.garnet/`.
  Test: plan for a one-path change with an existing recorder.

### Gap 8: one work directory per slug

- Symptom: two concurrent `live <slug>` runs share `out/<slug>/work` and would
  check out different branches in the same tree; the second run had to be
  restarted with `--work`.
- Code: `lib/commands.mjs:156` and `:363` (`workDirFor(slug)`).
- Proposed: default the work directory to `out/<slug>/work-<branch>` or take a
  lock file in `out/<slug>/work` and refuse with a clear message. Test: two
  plans for the same slug.

### Gap 9: dependency caches confound install-surface comparisons

- Symptom: `actions/setup-node` `cache: npm` and `astral-sh/setup-uv`
  (default cache on hosted runners) are keyed on the lockfile hash. Any
  dependency change guarantees a cache miss on commit 2 while commit 1 may hit,
  so destination deltas such as `storage.googleapis.com` or
  `releases.astral.sh` appearing or disappearing are cache effects, not
  effects of the change.
- Proposed: instrument mode records whether the job has a cache step and
  offers `--no-cache` (strip `cache:` inputs and `actions/cache` steps in the
  recorded job); `card` prints a `cache: present / stripped` line next to the
  capture line. Test: workflow fixtures with each cache form.

### Gap 10: matrix jobs collapse to one job on the App comment

- Symptom: continue `test` (four Linux Node versions) and servers `test` (one
  leg per package) both appear as `1 job` on the App comment. Whether the App
  collapses same-named legs or only one leg is recorded cannot be read from the
  comment.
- Proposed: `verify` counts matrix legs from the workflow file and compares with
  the recorded job count, reporting `legs recorded: k of n` as its own leg;
  this is also the input the capture-completeness contract needs.

### Gap 11: runner background traffic is not labelled

- Symptom: `provjobd`, hosted-compute agent addresses and `169.254.169.254`
  appear in destination deltas (codex `cargo-deny` +4, cline, opencode) and are
  indistinguishable from change effects in the card.
- Proposed: `card` carries a `runner background` bucket (documented list of
  processes and destination ranges) shown separately from the change's own
  processes; nothing is dropped, only labelled.

### Gap 12: `find` scores install surface from file names, not from the packages

- Symptom: every Dependabot change that touches `package.json` and a lockfile
  scores `+3 install-time execution surface changed` (60 of 60 continue
  candidates read on 2026-09-19); the three replayed here all carried it and
  none produced an attributable line. The score also ignores whether the
  recording job installs the touched directory (`/gui`, `/docs`,
  `/packages/openai-adapters` are not installed by `cli-pr-checks.yml` /
  `test`).
- Code: `lib/observe.mjs:101` and `:122` (`installSurfaces.length > 0`).
- Proposed: award `install-surface` only when the transition adds, removes or
  changes a package whose registry metadata has `hasInstallScript: true`
  (npm), an `optionalDependencies` platform package set, or a known
  binary-download post-install (Puppeteer, Playwright, esbuild, sharp, Prisma,
  sentry-cli, grpc-tools), and add an `outside recorder scope` reason with
  negative points when the touched directory is not installed by the ledger's
  recording job. Test: fixtures with `form-data` (no script) and `puppeteer`
  (script) transitions.

### Gap 13: a stale-base dependency change leaves the fork's manifest and lockfile disagreeing

- Symptom: servers 5 staged `src/fetch/uv.lock` as the change found it while
  `src/fetch/pyproject.toml` stayed at fork main (moved by upstream 4565 in the
  meantime). `Build fetch` on commit 2 failed with `The lockfile at uv.lock
  needs to be updated, but --locked was provided`. The recorded `test` job
  succeeded, so the record exists, but the check does not settle.
- Code: the base-distance guard at `lib/replay-pr.mjs:417` only fires when the
  fork is behind the change's base, not when the change's base is behind the
  fork.
- Proposed: when `commit 1 stages: the touched paths as the change found
  them`, also compare the sibling manifest of each touched lockfile (same
  directory: `package.json`, `pyproject.toml`, `Cargo.toml`) between the
  change's base and fork main, and warn (or require `--allow-stale-base`) when
  they differ. Test: fixture with a moved manifest.
